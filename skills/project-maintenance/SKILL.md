# 项目维护

让接手者能找到可靠现状、理解关键取舍，从正确的下一步继续。先读现有项目入口和它指向的状态、规则及必要证据。先确认实际交付物、怎么验收、谁会接手、哪里最容易失真，再决定需要动多少。

## 按请求选择动作

- **只读诊断**。找出实际妨碍接手或维护的问题，给出证据、影响和最小修法。评估、复盘和状态查询本身只授权核对和报告。
- **项目交接**。把当前结果、卡点和可执行的下一步写回已有负责位置。关键决策或被推翻的假设有既有记录时，更新该记录并留回查指针。单线项目可在一份现有文件内完成交接。是否需要整理其他部分由任务范围和实际障碍决定。
- **整体治理或新建项目**。先找具体的维护故障，再复用现有入口、状态和检查。按实际工作单元决定组织方式，例如交付里程碑、研究假设或内容主题。只有现有位置承载不了所需职责时才新增结构。遇到归属不明的材料，记录待确认项。迁移、合并、删除、改方向及外部操作沿用项目和用户的授权边界。

一次任务的常规收尾优先走项目原有流程。只有用户明确要求项目级维护，或者遇到会反复妨碍继续工作的维护问题时，才使用此技能。

## 让信息能被找到和修正

- **薄入口、按需读取**。入口让接手者知道从哪里开始、按什么边界做事、怎么跑和怎么验。证据、历史和细则留在对应位置，需要时沿指针读取。入口大小由宿主实际加载能力和接手成本决定。
- **关键状态有一个事实来源**。状态要与实际结果一致。总览可以写跨工作线的判断并引用各自状态。只有多个视图长期重复维护同一批结构化字段并易发生不一致时，才考虑生成总览、索引或做一致性检查。
- **结论可修正**。把新证据写到已有负责位置，判断它支持、纠正、缩限、取代还是推翻了什么。被取代的关键决定留可追溯的来去指针。跨工作线推广经验时写清成立条件。
- **用检查防止真实故障复发**。可确定判别且值得持续拦截的规则，优先接入项目已有检查。新增检查至少验证正常输入能通过、故意破坏目标条件能失败，并确认失败能传到调用者。报告实际运行过的检查、结果和覆盖范围。

## 交接验收

让没有旧聊天记录的接手者从项目入口和最少必要记录出发，回答四问。

1. 项目当前在做什么，什么已经有证据？
2. 卡在哪里，或目前没有卡点？
3. 下一步做什么，看什么结果才能判断做成了？
4. 开始前先读哪个位置，关键信息的来源在哪？

答案有冲突或找不到来源时，修复负责位置或指针，再检查一次。按需补充证据路径、确切命令和必要前置条件。只有实际让新会话检查过，才报告新会话验收通过。单线项目如何用一份状态记录完成交接，见[交接示例](README.md)。

交付时说明发现的维护问题、做了哪些动作、还有哪些决定待确认，以及接手者能否凭证据继续。输出长度和结构按任务规模调整。
