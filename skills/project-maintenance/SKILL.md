# 让项目持续生长

项目是持续生长的。对有 Agent 参与的项目，会话会结束，接手者会换，新一轮工作还会带来新的成果、证据和判断。一个活着的项目能把这轮真实发生的事交给下一轮，也能依据新证据修正原来的做法。维护的成效体现在项目往后是否仍能被理解、验证和改变。

## 骨架和血肉

**骨架相对稳定。** 它让接手者知道项目要解决什么、从哪里进入、以什么为准、有哪些约束、怎么验证。它可以分布在现有入口、测试、工作记录或工具里。接手时先读最少必要的信息，再按指针查需要的细节。相同的关键事实尽量由一处负责，让其余视图引用它。

**血肉随工作生长。** 实现、试验、内容、证据和决策随每轮工作更新。新证据可能支持、纠正、缩限或取代旧判断，重要变化要留回查线索。项目出现新的工作线、交接方式或验证难题时，骨架也可以随之调整。

## 结构随项目生长

同一个理念会长出不同的结构。研究项目可以围绕假设和证据组织，交付项目可以围绕用户流程和版本组织，内容项目可以围绕主题和审阅组织。用户或团队已经形成的习惯同样是选择结构的依据。

**维护已有项目，先看它实际怎么运转。** 了解现在是谁接手、平时从哪里找现状、哪条规则或检查已经起作用、哪处确实造成误判或返工。保留奏效的组织方式。一个指针、一处状态更新或一条已有检查能解决问题，就在当地解决。如果现有结构已经支撑继续工作，说明依据，即可完成这轮维护。更大的结构调整要能指出真实障碍、局部修复为何不足、迁移影响和验收办法，并按任务已给的范围行动。

**从新项目起步，让骨架先服务眼前的工作。** 根据实际产出、验证办法和接手者，留下足够的入口、事实来源与工作边界。等到新工作反复遇到具体问题，再增加对应结构。多个视图长期重复维护同一事实，可以考虑生成或一致性检查。资料已经难以搜到时，再考虑索引。可确定判别、值得拦截的重复故障，可以接入已有检查。

## 判断这次维护有没有用

结合用户的请求使用这些判断。只读评估给出问题、证据和建议。获得交接或改动授权时，把实际结果、卡点、下一步及证据写回已有负责位置。日常项目工作沿用项目原有流程。

交接时，好的检验是让没有旧对话的接手者从项目入口出发，能回答：**现在在做什么、卡在哪里、下一步做什么并怎样验收、开工前先读哪里。** 答案应能回查到事实。有冲突时，修正负责位置或指针。只有真实的新会话走过这条路径，才报告新会话接手验收通过。需要一种具体写法时，见[单线项目交接示例](README.md)。

如果本轮新增了可执行检查，在正常输入和有意破坏目标条件的输入上都试一遍，确认失败信号能传到调用者。报告维护后解决了什么接手或验证障碍，以及仍有哪些问题。
