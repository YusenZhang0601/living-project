# 漂移检查

> 它审的不是「这件事做对没有」，是「我们还在不在做那件事」。
> 判据只有一条：**能一句话说清「它现在能做什么，而上次审计时不能」吗？** 说不清，就是漂了。

## 一、三条不可谈判

1. **根由人给，不由仓读。** 仓库里的目标文件、STATUS、路线图都是**证据**，不是权威——它们自己会漂，而且往往漂得很诚实、很有条理。根只能来自 owner 的一句话，且必须能被反对。
2. **跑的人不能是漂的人。** 同一个人不能既跑又审。审计要么由人触发并由人裁决，要么交给一个**只拿到根、没有过程记忆**的 agent（见第八节）。自己反思自己在漂移处会自我确认。
3. **只产出「暂停并确认」，绝不自动改方向。** 审计结论是给 owner 的提案。改方向是 owner 的动作。这条来自同类工具的共识：maintainer tool, never an autonomous decision。

只读。审计期间不改代码、不改文档、不动方向。否则审计对象被自己动了。

## 二、第 0 步：拿到根

向 owner 要一句话，按这三个条件验收：

- **一句话。** 说不成一句，就是还没根。
- **可被反对。** 如果没有任何事实能让它错，它是口号，不是根。
- **不是当前活动的复述。** 「我们在做 X」里如果 X 等于最近在干的事，那是**现状**，不是根。

然后做一件事：**把仓里写的目标念给 owner 听，问他还是不是这个。** 今天这个项目就栽在这里——仓库写着「把论文压成可执行的底座」，听起来完全正确，而根是「一个原生为 agent 打造的操作系统」。差别不是措辞，是**要不要启动、要不要拥有磁盘、要不要能跑别的 agent**。

> 记录格式：`根：<一句话>。能推翻它的是：<事实>。`

## 三、第 1 步：清点——把所有在干的事摊开

取最近一段时间（建议：上次审计以来，或最近 20 次提交 / 3 个阶段 / 两周），按**工作单元**列出来，不要按文件列。每个单元标一个类：

| 类 | 定义 | 处理 |
|---|---|---|
| **根** | 直接让根从「不可能」变成「可能」 | 保留，且应是多数 |
| **推导** | 从根推出来的必要层，但不直接推进根 | 限量；问它是否挡在根前面 |
| **冻结** | 够用了，有已知天花板 | 记天花板，停止迭代 |
| **孤儿** | 既不服务根，也不是谁的必需品 | 停掉或归档 |

判据不是「有没有价值」，是**如果今天不做它，根会不会晚到**。不会晚到，它就不是根。

## 四、第 2 步：量配比

用**工作量**量，不用文字量：提交数、阶段数、会话时长、代码行、可执行产物的增量。

- 根类占比多少？
- 最近 N 个单元里，有几个**穿过了一条边界**（从一个层进到另一个层，或从设计进到运行）？
- 有多少单元是在**同一层内**做得更细？

一个健康的比例不是固定数字，但有一条硬线：**连续三个单元没有穿过任何边界，就是横向漂移。**

## 五、第 3 步：五类漂移源

任何一类成立就记一条，附**可核的证据**（命令、行号、提交号），不附形容词。

**D1 · 层叠代替竖切。** 设计 → 探针 → 视图 → 下一层，每一步都合理，合起来没有一个能跑的东西。判据：能不能指出一条从输入到输出的完整路径，哪怕很窄？

**D2 · 推导物当交付物。** 最漂亮的那个东西是从根推出来的第 N 层（一个视图、一份文档、一个索引），却被当成产品在打磨。判据：删掉它，根会不会晚到？不会，就是 D2。

**D3 · 权威与实现分叉。** 设计权威说 A，代码做 B，而两边都「有据」——通常是裁决记进了决策日志，权威文件没改。判据：把权威文件念给实现听，它们同意吗？下一个接手的人读权威，会不会把对的改回错的？

**D4 · 报告自证。** 执行者自己宣布「达成」，验收标准也是它自己写的。判据：这条结论有没有**由另一个人重跑过**？没有，它是提案，不是结果。

**D5 · 目标文件自己漂。** 最隐蔽的一类：STATUS 写的是真的，路线图也是真的，但它们描述的是**已经漂过去的位置**。判据：目标文件里还有「能做什么」的句子吗，还是只剩「说清楚了什么」？

## 六、第 4 步：停一件

选出**最像在前进、但不在根上**的那一件事。只有一件——列五件等于没选。

处理只有两种：

- **停**：孤儿。
- **冻结**：够用了。写下它的天花板（「在小账本上能用，10k 时 19 秒」），然后不再迭代。

不要删除。冻结的东西还要被用；删掉会让下一次审计重新发明它。

## 七、第 5 步：给一条竖切

下一步**不是又一层**，是一条穿过根的最窄竖切：从最外层（人看得见的东西）穿到最里层（系统真正拥有的东西），每一段都必须是**真的**，不是模拟的。

验收写法（照抄这个形状）：

> 这台机器冷启动进入 X → 挂上真实存储 → 一个真实外部使用者通过接口写一条 → 断电重启 → 读回来 → 显示出来。
> 全程在目标硬件上，并给数字：启动几秒、一次写几毫秒、内存多少。

替代方案也要写：如果竖切当前不可行（缺工具链、缺权限），写清**缺什么**，以及那条缺口的临时替代是什么、什么时候必须补上。**不要把「不可行」翻译成「先做另一层」。**

## 八、外部视角怎么造

两条路，优先第一条：

1. **人触发、人裁决。** owner 说「回头看一眼」，agent 执行第一到七步，人做最后判断。这是默认。
2. **盲审 agent。** 另起一个会话，只给它：根的一句话、最近工作单元清单（不给叙述、不给计划）、以及「用这些判断它是否还在为根做事」。它必须没读过这个项目的文档。判据是它能否**独立复述根**，以及能否指出至少一条你没意识到的推导物。

自己跑的那一版叫**自检**，只能用来决定「要不要请人看一眼」，不能作为结论。

## 九、漂移信号自检（便宜，可自己跑，不可信）

以下任一成立，触发一次正式审计：

- 连续 ≥3 个工作单元没有穿过任何边界
- 同一个词在每份文档里出现，却从没出现在可执行的东西里（「高性能」「交接包」「可迁移」）
- 一个阶段的验收项**全部**是文档
- 决策日志在增长，可执行的东西没增长
- 门禁变绿的速度快于系统变强的速度（测试只测测试）
- 最近的提交前缀清一色是 `docs:` / `test:` / `refactor:`，没有 `feat:` / `boot:` / `run:`
- 你在向人解释「为什么这很重要」，多于展示「它现在能做什么」
- 阶段名字越来越抽象（「可读性 pass」「治理轮」）
- 有东西只能由作者本人运行或阅读

## 十、输出模板

```
根：<一句话>。推翻它的事实：<...>

在干的事（最近 N 个单元）
  单元 | 类（根/推导/冻结/孤儿） | 证据 | 是否穿过边界

配比：根 x/N，穿边界 y/N，同层细化 z/N

发现（每条带证据与 falsifier）
  D? · <一句判断> · 证据：<命令/提交/行号> · 什么能推翻它：<...>

停一件：<哪一个>，停还是冻结，天花板是 <...>

竖切：<七节的形状>
缺什么：<不可行的那一段与它的临时替代>

我没验证的：<...>
```

## 十一、常见失败

| 失败 | 症状 | 修法 |
|---|---|---|
| **共谋** | 审的人读过全部过程，于是每个选择都「有理由」 | 换盲审；或让人先给根再让审的人说话 |
| **打分** | 给出「对齐度 68%」这类数字 | 用分类，不用分数。分数会被优化 |
| **礼貌** | 结论绕开「这件事不该做」 | 审计的价值就在这一句 |
| **全都要** | 列出七件该停的事 | 只选一件，其余进冻结清单 |
| **把冻结当删除** | 把「够用了」的东西整个扔掉 | 冻结 = 保留 + 记天花板 + 不再迭代 |
| **用审计代替决定** | 审完写了一份漂亮报告，方向没变 | 审计必须产出「停一件 + 一条竖切」，否则没做 |

## 十二、和现成技能的分工

同名的「漂移审计」大多审**一次改动**：`check`（diff 与目标对得上吗）、`validate-pr`（我们造的是对的产品吗）、`intent-drift-skill`（目标/计划/文件之间的对齐度）。它们都有外部锚：issue、PR、任务描述。

本技能审**一个方向**，没有外部锚，所以要向人要根。**一次改动该不该做，用上面那些；一个方向还该不该走，用这个。**

## 十三、项目参数归项目

本文件与具体项目无关。以下一律由项目自己定义，写进项目的入口协议，不要写进这里：

- 什么算一个「工作单元」（提交？阶段？会话？）
- 审计周期（多少轮、多少天）
- 根写在哪、由谁改
- 冻结清单放在哪
- 「穿过一条边界」在本项目里具体指什么

本技能的参考实现：一次真实的会话——四十九个决策、十三个 pass、一张精心打磨的视图，而那个项目要做的操作系统**一次都没有启动过**。人被问了一句「根是什么」，整套东西立刻重排了。
